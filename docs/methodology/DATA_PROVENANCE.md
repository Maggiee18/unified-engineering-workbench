# Example data: provenance, units and schema (Task B)

Both example files are **self created** for this assignment and contain no third
party or personal data. They are regenerated byte for byte by
`workbench_cli samples data` (C++ source: `src/app/cli_main.cpp`, functions
`makeHeatsinkStl()` and `makeSyntheticNodalCsv()`), and the generator immediately
re-parses them with the production parsers.

Licence: same as the project (released by the author for assessment use; no
restrictions on reuse).

## data/geometry/heatsink_bracket.stl

| Item | Value |
|---|---|
| Format | ASCII STL (`solid ... endsolid`), one solid |
| Content | finned heat sink bracket: 60 × 40 × 5 base plate, six 2.5 mm fins 25 mm tall, a cylindrical mounting boss (32 segments) and a web |
| Triangles | 224 |
| Units | millimetres by convention (STL itself is unitless; the UI shows "file units") |
| Bounds | x −14 … 60, y 0 … 40, z 0 … 30 |
| Normals | computed from right handed vertex winding (outward for the boxes) |
| Note | built from overlapping primitives, so it is a visualisation model, not a watertight manifold solid |

## data/thermal/synthetic_nodal_temperatures.csv

**SYNTHETIC DATA. This is not an ANSYS export.** It only follows the column layout of
an ANSYS Mechanical nodal temperature export so the importer can be demonstrated
without a commercial licence. The first comment line of the file states this, and
the UI shows that label in a warning box when the file is loaded.

| Item | Value |
|---|---|
| Schema | `node_id,x_m,y_m,z_m,temperature_C` (header required; any order; extra columns ignored with a warning; `#` lines are comments) |
| node_id | positive integer, unique |
| x_m, y_m, z_m | metres |
| temperature_C | degrees Celsius, must be ≥ −273.15 |
| Grid | plate 0.20 × 0.10 × 0.01 m, 41 × 21 × 3 = 2583 nodes |
| Field | T = 25 + 150 x + 60 exp(−r²/2e-4) − 200 z, r measured from (0.14, 0.05) m: a linear gradient plus a hot spot |
| Range | 23.0 … 106.0 °C |

Export notes for real ANSYS data: in Mechanical, right click a Temperature result >
Export > Text File, then rename the columns to the schema above (Node Number →
node_id, X/Y/Z Location (m) → x_m/y_m/z_m, Temperature (°C) → temperature_C) and save
as CSV with a dot decimal separator. Native .rst/.wbpj files are out of scope.

## Validation rules (both parsers, C++)

* Empty file, whitespace only file, header only CSV, STL with no facets: rejected
  with an explanation.
* Malformed structure: wrong keyword order, 2 or 4 vertices per facet, missing
  `endloop`/`endfacet`/`endsolid`, content after `endsolid`, multiple solids,
  binary STL, wrong field count, missing/duplicate CSV columns: rejected with the
  line number.
* Numbers parsed with `std::from_chars` (locale independent, so a German/Indian
  Windows locale cannot change "1.5"); NaN, Inf and overflow are rejected.
* CSV: duplicate node ids, non integer or non positive ids, temperatures below
  absolute zero are rejected.
* A rejected file never replaces the model currently on screen.

## Tested size limits

Limits: 64 MiB per upload (HTTP layer and parser), 1 000 000 triangles, 1 000 000
nodes. Measured on the Linux build in the cloud sandbox
(`results/csv/file_size_limit_tests.csv`):

| File | Size | Count | Result | C++ parse time |
|---|---|---|---|---|
| STL | 13.6 MB | 100 000 triangles | accepted | 123 ms |
| STL | 40.8 MB | 300 000 triangles | accepted | 631 ms |
| STL | 46.2 MB | 340 000 triangles | accepted | 470 ms |
| STL | 70.7 MB | 520 000 triangles | rejected, HTTP 413 "upload exceeds the 64 MiB limit" | |
| CSV | 20.9 MB | 500 000 nodes | accepted | 453 ms |
| CSV | 41.9 MB | 1 000 000 nodes | accepted | 1316 ms |
| CSV | 41.9 MB | 1 000 001 nodes | rejected, "node limit of 1000000 exceeded" | |

In practice the 64 MiB byte limit is reached first for STL (about 450 000 triangles
with typical formatting). Rendering time in the browser was not benchmarked
separately; a 300 000 triangle mesh stays interactive in Chromium with hardware
acceleration.
